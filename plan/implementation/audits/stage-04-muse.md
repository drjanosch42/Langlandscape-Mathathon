### F1 — critical — `stage-04.md:§1 S04-L3–S04-L7 deps` — placeholder cross-stage Lean names
**Location:** `stage-04.md:§0` para 1 and `stage-04.md:§1 Track L` rows L3, L7 (and DAG).
**Problem:** Dependencies `S03-L1`, `S03-L2`, `S03-L3`, `S02-L4b`, `S02-L7`, `S02-L4a` etc. are explicitly "placeholders" because no `stage-03.md` exists. `OVERVIEW.md:§1 §6` requires every Lean WP to cite the statement it formalizes and that the statement *exist* before the WP starts; cross-stage inputs that are not merged must be stubbed as registered hypotheses/`sorry`-stubs with explicit registry rows. The plan does not create those stubs as WPs, does not add `SORRIES.md`/`HYPOTHESES.md` rows for them, and therefore violates the interface existence rule and makes the DAG unverifiable. `SPLIT.md` does not define these S03-L* identifiers; they cannot be checked for label existence in `stage.tex`.
**Fix:** Either gate S04-L3/L7 on the merged `stage-03` Lean interfaces (make `stage-03 merge` a hard predecessor), or add explicit stub WPs `S04-S1/S04-S2` that create `sorry`-stubs for the exact declarations `S03.Ribet`/`S03.PhiComb` etc. with `SORRIES.md` entries and acceptance `grep sorry` allowed, and rewire L3/L7 to those stubs. Rebind once `stage-03.md` exists.

### F2 — critical — `stage-04.md:§0 Deviation` / `stage-04.md:§1 S04-L6,L8,L9` — undeclared `Hyp.InvLimExact` vs. incomplete interface
**Location:** `stage-04.md:§0 Scope` table note for `Hyp.MordLambdaFree`, `stage-04.md:§1 S04-L8` acceptance, `stage-04.md:§1 S04-L9` deps, `stage-04.md:§2 DAG`.

### F3 — major — `stage-04.md:§1 S04-C2` — acceptance check not mechanical / not sufficient
**Location:** `stage-04.md:§1 Track C` row `S04-C2`, acceptance column.
**Problem:** Acceptance is `PYCHK table: |S_s| = 2, 50, 1250; rk H_1 = |S_s|+1; rk_{Δ_s} e ℤ/125[X_s] equal for s=1,2,3 (value recorded, *computed*)`. The value is "*computed*" — no predetermined table is given in the WP or a referenced file. `OVERVIEW.md:§1` requires acceptance checks be mechanical where possible: `pytest` pass and numbers equal a *stated table (give the table or its file)*. An acceptance that records whatever the code computes cannot fail and does not verify `rk` constancy against an independent oracle (e.g. PARI/Sage or a hand-computed rank). Same pattern in `S04-C5` where the threshold `v_5|S_s| ≥ 2s-2` is necessary but not sufficient for the claimed `U_p* =5` action.
**Fix:** Fix the expected table in `code/results/s04/T3.json` (or `T3.expected.json`) before the WP runs: e.g. pre-state `rk_{Δ_s}=1` (or the actual known value from seed C2) and `rk eH_1 = rk eℤ[X'_s] -2 rk eℤ[X_s]` with numeric values. Make `PYCHK` compare `results/s04/T3.json` byte-equal to the expected table after `pytest`. Record provenance per `OVERVIEW.md:§6`.

### F7 — major — `stage-04.md:§1 S04-L5a/L5b/L6` — Lean-technical unsound claim about `MonoidAlgebra` local ring
**Location:** `stage-04.md:§1 S04-L5a` goal, `stage-04.md:§2 Build batching` note, `stage-04.md:§6 Risks` R2.
**Problem:** `S04-L5a` claims to prove `IsLocalRing (MonoidAlgebra ℤ_[p] G)` for a finite p-group `G` and then "f.g. projective ⇒ free over it". `Mathlib` has `IsLocalRing (MvPolynomial)` etc. but no instance `IsLocalRing (MonoidAlgebra R G)` for `R = ℤ_[p]`; the group ring of a p-group over a p-adic coefficient ring is local only after completing at `p` or assuming `R` is a field of characteristic p — over `ℤ_[p]` it is semi-local and the plan's cited lemma `Module.free_of_flat_of_isLocalRing` does not apply directly. The WP underestimates the gap: the fallback "prove for cyclic `Δ_s ≅ ℤ/p^{s-1}`" is mentioned only in R2, not in the WP's acceptance or outputs, so the WP would be judged failed even when the cyclic suffices. `S04-L5b` then assumes this result to get Prop freeA abstract.
**Fix:** Change `S04-L5a` goal to the sufficient case: `IsLocalRing (MonoidAlgebra ℤ_[p] (ZMod (p^(s-1))))` (cyclic p-group) with a reference to `MonoidAlgebra` + `Ideal.IsMaximal` argument, and add acceptance "either full p-group local instance or cyclic instance plus note that `Δ_s` is procyclic for p≥3, so Prop freeA holds". Move the general p-group claim to a stretch goal.

### F8 — major — `stage-04.md:§1 S04-L8` — acceptance insufficient for `lim` exactness; resource mis-estimate
**Location:** `stage-04.md:§1 S04-L8`, `stage-04.md:§0 Scope` deviation, `stage-04.md:§2 Critical path`.
**Problem:** `S04-L8` defines `Mord`/`Xord` as `Mathlib` limits and claims exactness of `lim` via "ML via vendored extract on `ZMod (p^m)` levels, then `m →∞`; or compactness". **Fix:** Split `S04-L8` into `S04-L8a` (define `Mord`/`Xord` as limits, prove `π_*` compatibility) and `S04-L8b` (exactness of `lim` via compactness), each with its own `LCHK` and with the Weil ML file as an explicit input. ### F9 — minor — `stage-04.md:§1 S04-C1/C2` — mathematical normalisation error risk not closed by acceptance
**Location:** `stage-04.md:§1 S04-C1`, `S04-C4`, `stage.tex:def:s04-Pk`.
**Problem:** `S04-C1` builds sparse `N_{U_p}` on `ℤ/p^m[X_s]` but `stage.tex:def:s04-e` and `lem:s04-ekills` depend critically on the fixed normalisation `N_{U_p}` = `U_p[x]= Σ_j [xϖ_j]` with `ϖ_j = ι_p^{-1} (p j; 0 1)` (the pushforward-compatible one). `S04-C4` tests `⟨d⟩ = d^{2-k}` for `k ≤6` (arithmetic ideal `P^ad_k`) but the acceptance for `S04-C1` only checks `e²=e`, `U_p e = e U_p`, `deg U_p = p deg` — none of which distinguish `N_{U_p}` from the seed's literal `U'_p = diag(1,p)` (which also satisfies those identities). The only witness for the wrong normalisation is `S04-C3` (H6) which is marked `TBD (default: mistral)` and not on the critical path, so a silent flip could pass `S04-C1`/`C2`.
**Fix:** Add to `S04-C1` acceptance: `PYCHK` that `U_p` commutes with `π_*: ℤ/p^m[X_{s+1}] → ℤ/p^m[X_s]` (Lemma Up (b)) — this fails for `U'_p` and is the discriminator. Propagate the same check to `S04-C2` provenance.

### F11 — minor — `stage-04.md:§2 Throughput / Resource limits` — potential violation of `≤3 Claude agents` and `≤2 Lean builds`
**Location:** `stage-04.md:§2 Throughput bound`, `stage-04.md:§2 Build batching`.
**Problem:** The plan proposes "a second coordinator for M/C/T" to mitigate worker-bound throughput. `OVERVIEW.md:§2 §4` limits stage parallelism to "≤3 Claude subagents per coordinator (Fable alone); a stage master runs ≤3 WP workers". Adding a second coordinator doubles the Lean-build concurrency: each coordinator's workers share the same node-wide `SLOTS=2` (`lean.lock` shared + per-checkout lock per `OVERVIEW.md:§3.4`). The plan's batching says "Slot 1 = critical-path batch, slot 2 = lfile iteration" — with two coordinators, 4 concurrent `lbuild`/`lfile` processes would contend for 2 slots, causing blocking not accounted for in the 12.2 h estimate. `≤2 local Lean builds` would be violated if both coordinators schedule builds simultaneously.
**Fix:** State that the second coordinator is *sequential* (takes over M/C/T after L WPs finish) or that total concurrent Lean processes remain ≤2 via the shared `slot.N` mechanism; add a resource check `resources.md: df/free` before each spawn per `OVERVIEW.md:§4`.
